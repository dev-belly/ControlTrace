# 审计时间线按实际 UTC 时刻排序

ISO 时间字符串的字典顺序不一定是事件顺序：`11:00:00+01:00` 是 UTC
`10:00:00`，而 `06:00:02-04:00` 是 UTC `10:00:02`。旧展示会把后者排在
前面。整秒的 `...00Z` 与小数秒的 `...00.050000Z` 也不能直接按字符排序。

0.2.10 根据解析后的 UTC 时刻排序，以证据 ID 和字段名打破同时刻的并列。
时间线上仍显示原始来源字符串；不能解析或为空的时间不加入时间线，但原记录
继续保留在关联证据中。控制谓词未改变，未知或非法业务输入仍须单独核实。

## 为什么需要格式 5

发现指纹包含完整时间线。若修正顺序，旧指纹就不再表示当前自动发现，之前的
复核保留为历史，当前状态返回 `pending`；不能因为来源 ID 没变就继承旧结论。
这里可能只改变了证据呈现的顺序，并不意味着来源时间被改写。

| 底稿格式 / 版本 | 时间线重放 | CSV 策略 | 证据关联 |
| --- | --- | --- | --- |
| 2 / 0.2.7 | 原字符串顺序 | 原单引号方式 | 无 |
| 3 / 0.2.8 | 原字符串顺序 | 原单引号方式 | 有 |
| 4 / 0.2.9 | 原字符串顺序 | 可见 `text: ` | 有 |
| 5 / 0.2.10 | 实际 UTC 时刻 | 可见 `text: ` | 有 |

格式 2–4 校验时重建原顺序，以保留原底稿与复核指纹的一致性，返回
`legacy_timeline_order=true`，命令行明确提醒它不保证 UTC 时间顺序。
新导出始终使用格式 5，返回 `legacy_timeline_order=false`。不要直接修改旧包
的格式号或清单来冒充升级；保留原包，再用当前源快照重跑并按新指纹重新复核。

[0.2.9 实际导出包](../tests/fixtures/README.md)保留混合时区的旧顺序和一条
程序生成的合成复核。回归同时验证旧包可核验，以及当前排序不会继承旧指纹
的关闭结论。这些是合成工程测试，不是实际审计意见或来源真实性证明。
