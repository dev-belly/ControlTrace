# 复核结论如何绑定证据

> 合成案例；这里的关闭状态是线索处理结果，不是企业审计意见。

## 业务问题：ID 没变，证据可能已经变了

发现 ID 根据控制、原因代码和对象 ID 生成。它方便关联同一条线索，但不代表证据内容不变。例如 D002 的变更工单后来修正了审批时间，即使依然命中“审批晚于上线”，发现 ID 仍然相同。仅按发现 ID 取最后一条复核，会把基于原抽取的 `closed` 结论自动套到修正后的证据上。

从 0.2.8 起，每次保存复核都会同时保存其自动发现指纹。指纹覆盖规则口径、关联源记录原值、时间线和自动判断。复核人、处理状态等界面附加字段不参与指纹，规则重跑的刷新时间也不参与。因此相同证据重跑保留结论，关联证据变化则返回 `pending`，原复核仍保留在历史中。

当前结论是**在当前指纹下，按 UTC 复核时间和复核 ID 排序的最后一条记录**。历史补录沿用原来的时间排序规则。其他线索的复核不影响本线索的编辑版本。若完整证据恢复为已复核的同一个指纹，对应历史结论也会重新适用；这里比较的是确切内容，不推断来源的可信性。

## 保存前核对编辑版本

界面首次展示复核表单时保存 `review_revision`，它概括当前证据指纹及该线索的全部历史记录。另一位复核者保存了新记录，或规则重跑后证据变化，当前表单就必须显式重新加载，避免把旧表单中的结论写到新证据上。

Python 调用者编辑之前读出的发现时，也应传入这个版本：

```python
from controltrace.store import get_finding, save_review

finding = get_finding("data/controltrace.duckdb", "F-2C5FD7D5834D")
assert finding is not None
save_review(
    "data/controltrace.duckdb",
    finding["finding_id"],
    "Demo Reviewer",
    "closed",
    "confirmed_exception",
    "Rechecked the current synthetic approval and deployment records.",
    expected_revision=finding["review_revision"],
)
```

版本核对、复核记录、证据指纹关联在同一 DuckDB 事务中提交。事务还实际递增该发现行的写入计数，使两个同时读取同一版本的连接发生写入冲突；仅执行字段值不变的更新可能被数据库优化掉，不能充当并发保护。失败会回滚复核及关联，使用者需重新读取当前记录。

`expected_revision` 是可选参数，用来保留旧 Python API；省略时，调用者明确按保存时的当前自动发现追加记录，不能获得旧表单检查。界面始终传入版本。这是本机同进程内多个连接的冲突控制，不是分布式协作或多人认证服务。DuckDB 的跨进程文件写入限制仍然适用。

## 旧数据与可复现底稿

旧数据库没有保存复核时的证据指纹。迁移保留所有原记录，但把它们视为证据版本未知，不从今天的源数据补造历史关联；使用者要重新评估当前证据后记录新结论。

从格式 3 起，底稿保留原 `reviews.json` 字段，同时增加 `review_evidence.json`：按发现和复核 ID 保存关联指纹，未知历史为 `null`。CSV 标明当前证据指纹和不适用历史数量，Markdown 明确显示当前结论与全部历史。校验器从包内源记录重放自动发现，重算指纹并独立选择当前结论；即使 CSV、底稿和文件哈希被一致修改，旧证据结论冒充当前结论仍会被拒绝。0.2.9 新导出采用格式 4，加强 CSV 字符串和表头的展示策略，JSON 原值与证据关联规则不变；[CSV 版本表](CSV_EXPORTS.md)列出细节。

格式 2、版本 0.2.7 的旧底稿继续支持原始重放；返回 `review_evidence_bound=false`，命令行也说明旧格式没有证据版本关联。格式 3 / 0.2.8 保留原 CSV 策略及证据关联重放。更早版本仍需其原版本校验器。这种兼容不会把旧底稿升级成拥有新保证的证据。

指纹和包内清单不能证明复核者身份、源系统真实性或防御同时重写所有内容的攻击者。新包只带当前源快照，保留的历史指纹并不等于保存了旧源快照。认证、签名和历史源版本归档仍是实际业务接入前需要单独解决的工作。

## 可以现场展示的验证

[回归测试](../tests/test_review_evidence.py)直接修改同一发现关联源行，验证发现 ID 不变、指纹改变、旧关闭记录保留、当前状态重新待复核；还覆盖两人同版本并发、绑定失败回滚、旧数据库迁移和重新计算哈希后的伪造关闭底稿。[界面测试](../tests/test_app.py)验证旧表单禁用保存，并在使用者主动重新加载后展示当前复核记录。

```bash
uv run --extra dev pytest tests/test_review_evidence.py tests/test_app.py -q
```

讨论项目时可以从这个具体问题展开：稳定业务 ID 与证据版本不同；追加历史与当前有效结论不同；事务原子性与读取后写入的并发冲突不同。每个判断都有代码路径和失败场景，而不是依赖合成数据的命中数。
